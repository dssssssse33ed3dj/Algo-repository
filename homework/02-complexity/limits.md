## 1. Заказы за сутки, `n ≤ 200 000`

Есть ли среди номеров хотя бы два одинаковых?

- **Проходит:O(n)**
- **Решение:использовать set для хранения встречных номеров**
- **Что мешало проще:вложенные циклы**
- **Почему это верно (с числом): при n = 200000 вложенные циклы сделают 200000^2 = 4 * 10^10 операций, в 4000 раз больше лимита. Set сделает O (n) = 2 * 10^5 мнгновенных операций**

## 2. Цены на складе, `n <= 100 000`

Найти три самые дешёвые позиции.

- **Проходит:** O(n log n)
- **Решение:** Отсортировать список и взять первые три элемента.
- **Что мешало проще:** Можно было бы трижды пройти по списку и найти минимумы, но сортировка проще и надежнее.
- **Почему это верно (с числом):** Сортировка займет n log_2 n операций. При n = 100 000 это 100 000 * 17 ≈ 1.7 * 10^6 операций. Это меньше 10^7, значит, укладываемся в лимит.

## 3. Архив чеков `n <= 10^7`, запросов `q <= 10^5`

Отсортирован. По каждому запросу сказать, есть ли такой чек.

- **Проходит:** O(q log n)
- **Решение:** Бинарный поиск (как в `06_find_receipt`).
- **Что мешало проще:** Линейный поиск по каждому запросу (два вложенных цикла).
- **Почему это верно (с числом):** Линейный поиск: q * n = 10^5 * 10^7 = 10^12 операций - это катастрофа. Бинарный поиск: q * log_2 n ≈ 10^5 * 23 = 2.3 * 10^6 операций. Влезает в секунду с запасом.

## 4. Координаты курьеров, `n <= 3 000`

Найти двух ближайших друг к другу.

- **Проходит:** O(n^2)
- **Решение:** Перебрать все возможные пары (два вложенных цикла, как в `08_closest_pair_distance`).
- **Что мешало проще:** Ничего, полный перебор здесь - самый простой и подходящий вариант (есть сложный алгоритм «разделяй и властвуй» за O(n log n), но он здесь не нужен).
- **Почему это верно (с числом):** n^2 = 3000^2 = 9 * 10^6 операций. Это меньше 10^7, значит, простой перебор успеет выполниться за долю секунды.

## 5. Одно число `k <= 10^9`

Сколько раз его можно разделить пополам до единицы?

- **Проходит:** O(log k)
- **Решение:** Цикл `while` с делением на 2 (как в `11_halving_steps`).
- **Что мешало проще:** Вычитать по единице в цикле.
- **Почему это верно (с числом):** Вычитание по 1 займет 10^9 операций (слишком долго). Деление пополам уменьшает число в 2 раза за шаг, поэтому шагов будет log_2(10^9) ≈ 30. Всего 30 операций.

## 6. Две накладные, `n <= 10^5` и `m <= 10^5`

Обе отсортированы. Собрать из них один отсортированный список.

- **Проходит:** O(n + m)
- **Решение:** Слияние двух списков с двумя указателями (как в `12_merge_sorted`).
- **Что мешало проще:** Сложить списки и заново отсортировать.
- **Почему это верно (с числом):** Слияние указателями: n + m = 2 * 10^5 операций. Сложение и сортировка: (n + m) log(n + m) ≈ 2 * 10^5 * 18 ≈ 3.6 * 10^6 операций. Оба варианта пройдут, но слияние работает быстрее и расходует меньше памяти.

## 7. Где модель ошиблась

Одно место, где модель ответила неверно или расплывчато, и как вы это
заметили.

- **Условие №:** 4 (Курьеры, n <= 3000).
- **Что ответила модель:** Предложила использовать алгоритм Разделяй и властвуй для поиска пары за время O(n log n), чтобы работало быстрее.
- **Что не так:** Это избыточно, так как при n = 3000 простой перебор всех пар дает всего 9 * 10^6 операций, что укладывается в лимит 10^7. Сложный алгоритм написать дольше, в нем легче допустить ошибку, а выигрыш по времени в данном случае не имеет значения.
- **Как поймали (расчёт или запуск):** Сравнил расчеты: 3000^2 = 9 * 10^6 < 10^7 (лимит). Понял, что простой двойной цикл справится с задачей.
